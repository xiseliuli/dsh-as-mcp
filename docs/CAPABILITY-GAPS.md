**The shape of the gap in one line:** the plugin can *start* a session's model turn and *read* its log.
It cannot address the session's **agent** — and `agent: Agent` is the scoping key for most of the
harness's non-model control surface.

### 1.4 Reach mechanics (why "available" means "on the context")

- Every capability is resolved lazily through `ctx.get(name)` (`types.ts:229-233`); `inject` is empty
  (`src/index.ts:32`) so a missing service is one tool error, not a refused load.
- `@Remote(...)` on a controller method is a **prototype marker only** — the decorator
  (`packages/typert/protocol/src/index.ts:174-184`) registers an initializer that calls
  `mark(prototype, method, ...)` (`:265-283`) and otherwise leaves an ordinary public instance method. So
  **every `@Remote` method is also host-callable in-process**. The plugin already relies on this:
  `sessionController.list/prompt/create/cancel` are all `@Remote` in the catalog and
  `driver.ts:425/456/380/500` calls them directly.
- Proof that a host plugin does this without the wire: `packages/client/ui-deliverables/src/present-open.ts:20`
  calls `ctx.sessionController.workspaceDesktop()` and `:74` calls `ctx.sessionController.openWorkspacePath(...)`.
- Therefore the reachable surface is **every service the host composition mounts**, and the *browser-only*
  surface is exactly the packages tagged `dsh.client` in their `package.json`. All 49 `@deepseek-ai/dsh-client-*`
  packages, plus `api-gateway`'s client half (`packages/api/gateway/src/client/index.ts:153`), are in that
  second set.

## 2. Ranked gaps that would add real capability

Ranking is by value to an outside agent driving DSH, weighed against implementation cost. Every row cites
the harness method; "Security" states whether exposing it lets the caller exceed the user's own permission
model.

### 2.1 The enabling layer — without this, most of the table is unreachable

**G1. Resolve a session to its live `Agent`.** `sessionController.resolveAgent(sessionId)` →
`{ agent } | { error }` — `api-catalog.ts:1449`; type `ApiSessionAgentResult` at
`api-catalog.ts:3651`; implementation `packages/api/session-controller/src/agent.ts:170`, resuming a cold
session at `:186-215`. `ctx.agents.get(id)` (`api-catalog.ts:322`) is the non-resuming lookup.

`agent` is not an object with methods — it is `{ id: SessionId }` (`packages/core/agent/src/types.ts:13-16`).
Its value is *scoping*: `ctx.tools`, `ctx.commands`, `ctx.skills`, `ctx.jobs` and `ctx.goals` all key
per-agent layers on it. Resolving it is what turns "a session I can prompt" into "a session whose agent I
can address".

*Security:* none new. It is the identity the session already runs as, and every downstream call still
passes through the same permission preset, sandbox and approval policy. It does not widen authority.

*Sketch:* no tool of its own. It is the internal bridge that makes G2–G4, G12–G14 possible.

### 2.3 The gap that looks big and is not: session search

`ctx.sessionQuery.searchSessions` `:1753` / `searchEvents` `:1759`, and
`sessionController.search` `:1467`, look like the headline capability — "find where we discussed X across
every past session". **They do not work in the Desktop profile.** Verified:

- `packages/session-query/session-query-sqlite/src/index.ts:334-342` — `_assertSearchEnabled()` throws
  `SESSION_QUERY_SEARCH_DISABLED` when `openAt === 'never'`, *before any SQLite work*.
- It is called from exactly two places: `searchSessions` (`:272`) and `searchEvents` (`:300`). Every other
  `sessionQuery` method is ungated.
- The Desktop profile sets exactly that: `packages/bundle/base/cordis.patch.yml:129-133` sets
  `openAt: never`, and `packages/bundle/web-app/cordis.patch.yml:22-30` restates it.
- `sessionController.search` reaches the same gate: `packages/api/session-controller/src/list.ts:203`
  calls `provider.searchSessions(...)`.

So a `session_search` MCP tool would be dead on arrival for every Desktop user, and would only work after
the user edits a bundle patch. Because `full-text search is opt-in` is itself the harness's deliberate
posture, the correct action is **not** to build the tool. The ungated floor — `sessionQuery.listSessions`
`:1765`, `filterSessions` `:1778`, `readSession` `:1771`, `readEvent` `:1835` — is already reachable via
`session_list` + `session_messages`.

## 3. Should stay absent — and why

These are not "hard to build". They are the ones where building them would make the bridge *more
dangerous than DSH's own agent*, because they act on the configuration or credential plane rather than on
the user's work.

| Surface | Citations (015) | Why it stays absent |
| --- | --- | --- |
| **`typert` generic RPC** | `typertGateway.invoke` `:2730`, `.stream` `:2737`, `typert.register/resolve` `:2669-2706` | **The most important refusal.** A generic `{namespace, method, args}` invoker reaches *every* `@Remote` method — including every item below. Exposing it makes the entire rest of this list decorative. Any capability added must be a named, schema-validated tool, never a passthrough. |
| **Credentials** | `credentials.resolve` `:738`, `describe` `:744`, `set` `:750`, `readRecord` `:760`, `listRecords` `:772`, `modifyRecord` `:778`; `credentialsController.describe/set/unset` `:796-809` | Returns and stores the user's API keys. A tool that hands a calling agent the DeepSeek key is a categorically worse version of the thing already deliberately avoided. |
| **OAuth / account authorization** | `authorization.begin` `:588`, `authorization.registerFlow` `:564`, `describe` `:577` | Completes a login flow and mints account access. Grants authority the caller never had. |
| **Approval policy writes** | `approval.setPolicy(agent, 'ask'\|'never')` `:444`, `approval.overrideOf` `:456` | A tool that sets `never` for an arbitrary session lets a remote caller silence the user's own approval prompts. | **Permission wideners** | `permissionPresets.set(session, name)` `:1376`; the `/permission` command `packages/interaction/permission-presets/src/index.ts:257` | Climbing from `workspace-write` to `danger-full-access` is precisely the escalation an outside caller must not be able to perform on its own behalf. | **Settings writes** | `settings.update/replace/mutate` `:2043-2055`; `settingsController.update/replace/mutate` `:2081-2095` | The config plane: permission presets, sandbox policy, plugin config, model routes. | **Opaque storage** | `storage.mount/form` `:2228,2234`; `storageDomain.open/get` `:2247,2253` | Untyped key-value writes over the harness's own storage backends. There is no schema to validate against and no undo; a caller could corrupt plugin state. |
| **Raw session persistence** | `sessionPersistence.create/open/flush/stat` `:1597-1624`; `sessions.create/prepare/enter/announce` `:1873-1894` | Bypasses `sessionController`'s preset, policy and identity admission. `sessions.enter(session)` additionally rewrites the *ambient* session for the calling fiber, which in a host plugin means the plugin's own context. `sessionController.create` is the sanctioned door. |
| **Raw agent composition** | `agentLoop.create/createAgent/resume` `:114,120,126` | Composes an agent directly, skipping the session controller's model/preset admission. Same reason. |
| **Subprocess seam** | `subprocess.spawn` `:2391`, `spawnTerminal` `:2398`, `resolveExecutable` `:2385` | The layer *beneath* `ctx.shell`. `shell` applies the sandbox and the approval policy; `subprocess` is what the shell executor uses after it has. Exposing it would route around the exact fence `shell_run` respects. |
| **HTTP route registration** | `webServer.register/registerUpgrade/registerFallback/tapIndex` `:2814-2832` | The MCP endpoint is itself mounted on this server (`http.ts:232-246`). A caller that can register routes can shadow or impersonate the endpoint, or serve content from the harness's origin. |
| **Feedback writes** | `messageFeedback.put/delete` `:1331,1337`; `sessionFeedback.record` `:1571` | Writes to the user's own review records. An outside agent's opinion is not the user's; injecting it pollutes data the user reads as their own. |

**One borderline item, called out rather than filed.** `userQuestions.ask(request)` `:2750` (DSH's own
`ask_user_question`, `packages/interaction/tool-ask-user/src/index.ts:21`) would let a blocked outside agent
route a decision to the human who is actually in the DSH UI — genuinely new cross-agent human-in-the-loop,
and arguably the most interesting item on this page. It is also the one that lets a remote agent pop a
modal at the user unprompted. **If it is built, it must be default-off behind a config flag, exactly like
`approval.policy`, and rate-limited.** I would not ship it in the first pass.
`directoryPickerController.pick` `:854` is the same intrusion with less value (`workspace_create` already
takes a path) — skip it outright.

## 5. Not applicable to a host-side bridge

These are real harness capabilities that a `ctx.get`-based host plugin structurally cannot reach, so
listing them as plugin gaps would be a category error.

- **All 49 `@deepseek-ai/dsh-client-*` packages** — tagged `dsh.client` in their `package.json`; they are
  the browser roster scanned into `window.__DSH_BOOT__`, not host services. UI theme, layout, renderer,
  sidebar, chat, conversation, trajectory, tool cards, settings pages, and the locale bundle all live here.
- **`ctx.remote` and every `ctx.remote.<namespace>`** — the browser RPC client
  (`packages/api/gateway/src/client/index.ts:153`, namespace services at `:547`, `:659`). It needs the
  connection carrier and a live browser session (`:157`, `:222-231`). A host plugin that wants the same
  data calls the host service directly, which is what §1.4 establishes.
- **Client-side key shadowing** — the browser bundle mounts a client `sessions`
  (`packages/api/session-controller/src/client/index.ts:80`) and a client `workspaces`
  (`packages/api/workspace-controller/src/client/service.ts:88`) that reuse the host key *names* in a
  different bundle. Whichever half you are in decides which one you get; the host half gets the host one.
- **`clientModules`** `:602` — serves client bundles and the boot graph. Browser infrastructure.
- **`api/remotes`** — no service key on either plane; it only *assembles* the client mount
  (`packages/api/remotes/src/client/index.ts:143-159`).
- **`fileUploads.upload`** (the `@Remote` variant, `:922`) — needs the browser's agent resolver.
  `fileUploads.uploadStream` `:928` is the host-callable sibling, and it is what gap #18 would use.
- **`inspector`** `:1117` — the Cordis runtime tree reader. Developer tooling, and adjacent to the
  code-execution refusal above.
- **`productTelemetry`**, `client-hmr`, `client-file-upload`, `host-open-in-app`,
  `host-directory-picker-auto` — surface plumbing with no agent-facing semantics.

Note that `directoryPickerController` `:854` and `userQuestions` `:2750` are *host-callable* — they are
excluded in §3 on intrusion grounds, not for being unreachable. The distinction matters: one is a
structural limit, the other is a judgement call that a future maintainer could reasonably revisit.

## 6. The MCP protocol surface

The server registers **tools only** (`tools.ts:98`). Below is what the installed
`@modelcontextprotocol/server` 2.1.0 actually supports, and whether each addition is real value or
ceremony *for this server's actual callers*.

> **Reading the SDK citations.** The `dist/` filenames below are content-hashed
> (`createMcpHandler-Bt6U_Fqb.d.mts`, `src-D-y6h4N7.mjs`) and will change on any SDK bump. They are
> accurate for 2.1.0 as installed; re-locate by symbol name (`McpServer.registerResource`, `ServerContext`,
> `CreateMcpHandlerOptions`, the notification-method registry) after an upgrade rather than by line.

### 6.1 Resources — available, but structurally hobbled here

The SDK backs both shapes: `McpServer.registerResource(name, uri, config, readCallback)` for a static
resource and `registerResource(name, template, config, readCallback)` for a resource template
(`dist/createMcpHandler-Bt6U_Fqb.d.mts:3321`, `:3325`), plus `Server.sendResourceListChanged()`
(`:3209`) and `McpServer.sendResourceListChanged()` (`:3453`).

The honest verdict is **no, except possibly one**. Two reasons:

1. **Subscriptions cannot work in this deployment.** The plugin runs `createMcpHandler(..., { legacy: 'stateless' })`
   (`http.ts:82`), and the SDK documents that in that mode "GET and DELETE (2025 session operations) are
   answered with `405` / `Method not allowed.`" (`dist/createMcpHandler-Bt6U_Fqb.d.mts:3903-3919`). The
   standalone GET SSE stream is what carries `resources/subscribe` and `notifications/resources/updated`.
   With no stream and a **fresh `McpServer` built per request** (`http.ts:69-74`), there is no place for a
   change notification to land. Resources would be read-once documents with no liveness.
2. **For an agent caller, an addressable document is not capability.** A resource returns the same bytes
   `session_messages` or `file_read` already return. Resources earn their keep for clients that browse or
   preload context, or that need a `mimeType`-typed attachment — not for an LLM that already has tools.

If exactly one is worth it, it is an addressable session transcript
(`dsh://session/{id}`), because "poll with `session_messages`" becomes "address it". Resource *templates*
(`dsh://session/{id}/events?limit=`) add argument completion via `CompleteResourceTemplateCallback` — more
ceremony on top of a surface that is already marginal. **Do not build resource templates.**

### 6.2 Prompts — the wrong shape for this audience

`McpServer.registerPrompt(name, {argsSchema}, cb)` is fully supported
(`dist/createMcpHandler-Bt6U_Fqb.d.mts:3407`, `:3417`). Backing the agent-preset catalog
(`agentPresets.list()` `:139`) or the skill catalog (`skills.list()` `:2185`) as MCP prompts is a
*technically correct* mapping and the wrong product decision.

MCP prompts are **user-invoked slash commands in the client**. The caller of this server is an agent, and
an agent does not call `prompts/get`. Meanwhile the actually useful version of both ideas is a **tool**:
`skill_list` + `skill_read` (gap #12) let the outside agent *discover and load* a skill body on its own
initiative, which is the whole point. Prompts would put the skill behind a human click in a different
application.

Ship it only if the author explicitly wants human-facing MCP clients (Claude Desktop and similar) to
surface DSH presets as slash commands. That is a real but different audience, and it should be stated as
such rather than smuggled in as "MCP completeness".

### 6.3 Progress and notifications — cheap, real, worth it

`notifications/progress` is a first-class notification method in the SDK's registry
(`dist/src-D-y6h4N7.mjs:2216`). A tool handler receives `ctx` and can emit one through
`ctx.mcpReq.notify({ method: 'notifications/progress', params: {...} })` — `McpRequestContext.mcpReq.notify`
is declared at `dist/createMcpHandler-Bt6U_Fqb.d.mts:2201` and is part of the `ServerContext` a tool
callback receives.

Delivery works here, which is the non-obvious part:

- On the modern era, `responseMode: 'auto'` (the default) "upgrades to an SSE stream" as soon as the
  handler emits a related message before its result (`:3920-3933`).
- On the legacy leg the plugin actually serves, `enableJsonResponse` defaults to `false`
  (`dist/index.mjs:363`, `:382`), so the response is **already** SSE regardless of `responseMode` — which
  is exactly what the code comment at `http.ts:79-81` observes.

So the machinery is present and the framing already supports it. The catch is the client: progress
notifications only fire if the caller sent `_meta.progressToken`, which most MCP clients do not do for a
`tools/call`.

**Verdict: add it, and be honest about the conditionality.** `session_prompt` may wait up to
`promptTimeoutMs: 900000` (set in this machine's profile patch, `~/.dsh/profiles/desktop/cordis.patch.yml`), and the driver
already re-reads the session log every 200 ms (`driver.ts:470-494`, `TURN_POLL_INTERVAL_MS` at `driver.ts:22`).
Emitting a progress tick per poll is a few lines, costs nothing, lets a client reset its own request
timeout (`RequestOptions.resetTimeoutOnProgress`), and turns a silent fifteen-minute wait into an
observably-live one.

What is **not** worth building on top: fake token-level streaming. The harness has a real streaming
surface — `sessionController.follow` returns `AsyncIterable<SessionFollowFrame>` including
`assistant-stream` frames (`api-catalog.ts:1552`, `SessionFollowFrame` at `:5182`) — but MCP has no
streaming *tool result*. Smuggling token deltas through `notifications/progress` would abuse the
notification to carry payload. If incremental output is wanted, the honest shape is a bounded long-poll
tool (`session_wait`) over that stream, or nothing.

### 6.4 Structured tool output and `outputSchema` — real, modest, cheap

`registerTool` accepts `outputSchema` alongside `inputSchema` (`dist/createMcpHandler-Bt6U_Fqb.d.mts:3359`,
`:3363`), handlers may return `structuredContent` (`:3353`), and the SDK **validates** the output against
the schema (private `validateToolOutput`). Today the plugin returns everything as one
pretty-printed JSON text block (`tools.ts:63-65`), so a caller gets a string it must parse and a schema
documented only in prose.

Worth doing. It gives machine-checked shapes, better rendering in clients that understand
`structuredContent`, and it *pins the contract* in code — which the author clearly values, given how much
of `driver.ts` is about contract fidelity. Two constraints:

- `ok()` in `tools.ts:63-65` must be extended to emit `structuredContent` as well as the text block; the
  text block should stay for clients that ignore the structured field.
- Only apply it to **closed-shape** outputs — `dsh_info`, `session_create`, `session_list`, `file_list`,
  `shell_run`. Tools whose result embeds arbitrary file or transcript content are better left loose,
  because a validation mismatch turns a successful call into a protocol error.

### 6.5 The rest of the SDK surface

- **Tasks** (`tasks/get`, `tasks/result`, `tasks/cancel`, `CreateTaskResult`, `TaskAugmentedRequestParams`)
  exist in 2.1.0. They are the protocol-native answer to "long-running operation" and would be a more
  principled home for gap #4 (background shell) than a bespoke handle registry. **Inferred:** I did not
  trace task support through `createMcpHandler`'s per-request factory, and a stateless per-request server
  is exactly the shape that makes task state hard. Treat as a research item, not a plan.
- **Elicitation and sampling** (`ServerContext.mcpReq.elicitInput` / `requestSampling`,
  `dist/createMcpHandler-Bt6U_Fqb.d.mts:2216+`) are deprecated on the 2026-07-28 era and "throw on a
  2026-07-28-era request", replaced by `input_required` results. `elicitInput` looks like the right shape
  for "ask the human" — but it asks the **calling client's** user, not the DSH user, so it does not solve
  the `ask_user_question` problem in §3. `requestSampling` would ask the caller's client to run an LLM
  completion on DSH's behalf, which is a strange inversion with no clear consumer.
- **Bearer-token auth is the entire authorization model** (`http.ts:91-98`). Worth stating plainly: every
  gap above is gated by *one* secret, and adding gap #1 (arbitrary DSH tool invocation) makes that one
  token worth much more. If the top of the ranked list is built, splitting the token per tool group — or
  at minimum offering a read-only token — stops being a nicety.

## 7. Version note: 0.1.5-rc.1 vs 0.1.7-rc.2

`package.json` declares `dsh.compatibility.dsh: ">=0.1.5-rc.1"`, so the plugin claims to load on both.
One claim is already false.

**Breaks on 0.1.7-rc.2, and it matters:**

- **`ctx.shell.run` no longer exists.** 0.1.5-rc.1 has `shell.resolve` `:2123`, `shell.run` `:2129`,
  `shell.start` `:2135` (`api-catalog.ts`). 0.1.7-rc.2 has only `shell.resolve`
  (`dsh-harness-ref/.../api-catalog.ts:2532`) and `shell.execute(spec): Promise<ShellExecution>` (`:2538`),
  where `ShellExecution extends ShellProcess { result(): Promise<ShellRunResult> }` (`:6890`). Both
  `run` and `start` are gone. **`driver.ts:653-659` calls `shell.resolve` then `shell.run`, so `shell_run`
  breaks on 0.1.7-rc.2.** Any background-shell work (gap #4) must be written against both shapes:
  `start(spec)` on 015 and `execute(spec)` on ref, with `result()`/`readOutput()` unified behind one local
  adapter — the same pattern `types.ts` already uses for `readBytes` vs `readByteRange`.
- **`codeRuntime` and `e2b` services are removed** (015 `api-catalog.ts:646`, `:874`), replaced by
  `ptcRuntime` (ref `:1740`). Nothing in the plugin uses them and `describeCapabilities` does not probe
  them, so there is no impact today — but a future "run code" tool must target `ptcRuntime`, not
  `codeRuntime`.
- **`sessionController.updateQueue` became async** (gap #20): 015 `:1534` returns
  `SessionUpdateQueueValue`; ref returns a `Promise`. Await it.
- `agentPresets` lost 6 methods, `agentTeams` lost 3 `@Remote` methods, `workspaceFiles` lost `readAll`
  and `readRelated`, and `jobs` changed shape (`JobSnapshot` → `JobView`, plus `readAt`/`events`/`remove`).

**Stable across both — every gap I recommend against these is version-proof:**

`sessionQuery`, `goals`, `commands`, `skills`, `tools`, `web`, `approval`, `planMode`, `sandboxPolicy`,
`llm`, and `terminals` are byte-identical between the two catalogs. In particular `ctx.tools.execute`
(gap #1), `ctx.commands.execute` (gap #2), `fs.editText` (gap #3), `ctx.web.search/fetch` (gap #6) and
`ctx.sandboxPolicy.resolve` (gap #7) are safe to build against 015 today and will still be there on ref.

**Ref-only, so do not build against them yet:**

- **`ctx.fs.watch(target, changed, signal)`** (ref `:1042`) — a file/workspace change stream. **Does not
  exist in 015**, so a "watch this directory" tool cannot be written against the authoritative version.
- `terminalController` (ref `:3001`) — a browser-facing PTY controller with `create`/`follow`/`write`/
  `resize`/`close`; distinct from the unchanged agent-owned `ctx.terminals`.
- `schedule` (ref `:1812`) with `schedule_create`/`schedule_list`/`schedule_delete` tools — durable
  reminders. Opt-in: its bundle row is `disabled: true`.
- `jobController` (ref `:1269`) — remote job observation, which is what gap #13 approximates on 015.
- `mcpResources` (ref `:1476`) — lets DSH's agent read resources from the MCP servers *it* is connected to.
  The mirror image of this whole document, and ref-only.
- `browserUse` (ref `:546`) / `computerUse` (ref `:672`), `ssh` (ref `:2724`), `workspaceChanges`
  (ref `:3477`), `configEditor` (ref `:685`) and `pluginManager` (ref `:1608`). The last two are squarely
  in §3's absent column.

**A correction to the brief's premise, worth recording:** `deliverables` is not a service key in either
version — it is only a package group; the real new service in that area is `workspaceChanges`. And
`terminals` was *not* removed in ref as one might expect from the package reshuffle; all nine signatures
are identical.

## 8. What I would build next

**The short list, in order.**

1. **`dsh_info` grows a posture and catalog block** — gaps #7, #8, #14, #15. Add
   `sandboxPolicy.defaultMode` / `resolve()`, `permissionPresets.current()`, `llm.listProviders()`,
   `agentPresets.list()`, and live agent counts. It is read-only, ~40 lines, version-stable, and it fixes
   the worst usability defect in the current surface: `session_create`'s `provider`, `model` and
   `agentPreset` are blind strings.
2. **`dsh_tool_list` + `dsh_tool_call`** — gap #1, on top of the `resolveAgent` bridge (G1). This is the
   change that turns the bridge from a chat relay into an operator console. Ship it with an explicit
   allow-list, and start read-mostly (`read`, `glob`, `grep`, `edit`, `read_image`) before opening `bash`.
3. **`file_edit`** — gap #3, plus ranged `file_read` — gap #15. Small, version-stable, and it removes the
   single largest per-call token cost in the current surface.

Then, in rough order: `shell_start`/`shell_output`/`shell_kill` (gap #4, written against both shell
shapes), `file_read_image` (gap #5), `web_search`/`web_fetch` (gap #6), `session_fork` (gap #9), and
progress notifications (§6.3) — all cheap and none of them contentious.

**What I would refuse to add.**

**`typertGateway.invoke` as a tool** — a generic `{namespace, method, args}` RPC passthrough. It is the one
addition that would silently void every other refusal on this page: a caller with that tool can reach
`credentials.resolve`, `settings.mutate`, `approval.setPolicy`, `permissionPresets.set` and
`webServer.register` without any of them ever being named in a tool schema, an audit trail, or this
document. Every capability worth having here is worth naming, typing and allow-listing individually. If a
future maintainer is ever tempted because "it makes the surface complete", the answer is that completeness
was never the goal — `driver.ts` is 851 lines of careful contract work precisely because the author chose
specificity over generality.
